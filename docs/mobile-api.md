# NLB mobile API client (experimental)

The `mobile` commands call the mKlik JSON API instead of scraping the web
site. Everything here comes from static analysis of the NLB mKlik APK
(version 3.3.41), which is not part of this repository. No live account was
used. Treat the commands as a spike, not as a supported interface.

## Commands

```sh
nlbcli --profile personal mobile login --username <USER> --otp <CODE>
nlbcli --profile personal mobile accounts
nlbcli --profile personal mobile balance <ACCOUNT>
nlbcli --profile personal mobile transactions <ACCOUNT> --start 01.10.2026
```

`--otp` is the one-time code generated by mKlik on the user's phone. `--serial`
is optional. All reads print JSON to stdout. A missing or expired mobile
session exits with code `3`.

The token is saved in `~/.nlbcli/profiles/<profile>/mobile.json` with mode
`0600`. It is separate from the web session in `session.json`.

## Transport

| Item | Value | Source |
| --- | --- | --- |
| Base URL | `https://mbanking.24x7.com.mk` | `zc.a`, `ClientConfig` |
| Login | `POST /nlb-ret/IdentityAPI/api/v1/identity/login` | `uc.k.login(LoginRequest)` |
| Assets | `GET /nlb-ret/IdentityAPI/api/v1/info/assets` | `uc.k.getAssets` |
| Dynamic read | `POST /nlb-ret/InfoAPI/api/v1.0/dynamic/get-secure` | `zc.a.ENDPOINT_WEB_API_GET_SECURE` |
| Read headers | `Authorization: Bearer <token>`, `lang: mk` | `hr.asseco.utils.t1.getAuthorizationToken` |

Read requests take an `action` plus a filter:

| Action | Purpose |
| --- | --- |
| `account-details-checking` | Account balance |
| `account-details-cms` | Card account details |
| `account-transactions-checking` | Account transactions |
| `account-transactions-cms` | Card transactions |

Transaction filters use `yyyy.MM.dd` dates and `sorter: "date"`. The CLI
accepts `dd.mm.yyyy` and converts.

## Request authentication

Login adds three headers. They are an HMAC over a timestamp, method name,
method type and random value:

```
timestamp  = UTC "yyyy-MM-dd HH:mm:ss"
payload    = timestamp + "\n" + methodName + "\n" + methodType + "\n" + rand
key        = swapHalves(WEB_API_SECRET) as UTF-8
Authentication = "1:" + base64(HMAC-SHA256(key, payload))
```

`methodName` is `Login` and `methodType` is `POST`. `rand` is a UUID.

The key is derived from `WEB_API_SECRET`, which `libSecureImpl.so` returns for
`Java_hr_asseco_android_ClientConfig_webApiKeyReleaseTutunska`:

```
WEB_API_SECRET = 8346C8F846734604D9AE5E1D10490814
```

## Body encryption

Some app endpoints wrap JSON in an encrypted envelope:

```
request = base64( iv || AES-256-GCM(key, json) || tag )
```

The key is the same swapped secret, the IV is 12 random bytes, and the tag is
16 bytes. `src/mobile/protocol.ts` implements both directions. The login and
read calls used by this CLI send plain JSON, matching their Retrofit method
signatures.

## Known gaps

These items are inferred and not verified against a live server:

- Login body field names follow the bank model classes (`mCredentials`,
  `mOTP`, `mSerial`). The app's own login also runs the SDK token protocol.
- Device info, UUID and serial values are accepted or rejected by device
  binding. The CLI sends a stable random UUID per profile.
- `Value.amount` is a number in bank units. The scale is not confirmed, so the
  CLI prints wire values.
- Card and savings actions are selected by the account number and `accType`.
  Other account types may need a different action.
- The app uses an additional SDK JSON-RPC transport for login. This CLI uses
  the REST endpoints only.

## Device binding

- Each mKlik install holds a private token in the Android keystore. `getTokenSN()`
  returns its serial, and login sends it as `mCredentials.mSerial`.
- The client models a list of user devices (`Devices{deviceId, deviceName,
  deviceDescription, roles}`) and the activation flow reads it. The SDK also
  defines user-device create/read/update/delete error codes. No single-device
  limit appears in the client.
- The CLI has no token. It sends `--serial` when supplied and a random UUID per
  profile.
- Unverified: the server may bind sessions to registered devices, and a new
  login may end an earlier session. The app has an `endsession` endpoint at
  `OnboardingAPI/api/v2/users/endsession/` and session-expired error codes.

## Security

The secret is shipped inside the APK and is the same for every install of this
bank variant. Do not treat it as a credential. Use this client only with your
own account and only where the bank's terms allow it.
